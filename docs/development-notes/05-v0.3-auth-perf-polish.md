# v0.3 — Auth, performance, and UX polish

These are the changes that landed in v0.3 after the initial portfolio build.
Each one came from a real user observation or a real failure I measured.

## 1. Authentication (was open, now JWT)

**Before**: the chat app was open. Anyone with network access to port 8090
could use the agent. The original "API key" mode (env `CHAT_API_KEY`) was
opt-in and didn't even require a user.

**Why change**: any portfolio you put online or demo on a public network
needs at least basic auth. The reviewer "el que lo ve" should not be able
to query your private knowledge base without consent.

**What I built**:
- `scripts/auth.py` — users in `data/users.json` (scrypt-hashed, never plaintext)
- `POST /api/auth/login` → JWT (HS256, 24h expiry)
- `get_current_user` FastAPI dependency on all non-public endpoints
- Login screen full-screen in the SPA, hides the chat until login
- `authFetch()` wrapper in JS adds `Authorization: Bearer <token>` to every
  request automatically
- 401 → automatic redirect to login (no need to refresh manually)
- Logout button in the sidebar

**Why no external lib** (no PyJWT, no bcrypt, no Auth0):
- `hashlib.scrypt` is stdlib, GPU-resistant, perfect for portfolios
- Hand-rolled JWT is ~30 lines of code with no supply chain risk
- Auth0/Clerk are overkill for a single-user dev app

**Lessons**:
- Constant-time comparison is non-negotiable for password/signature checks
- sessionStorage > localStorage for tokens (cleared on tab close)
- Rate limit the login endpoint (10/min) — even on localhost, prevents
  accidental loops from blocking real users

See [`app/docs/AUTH.md`](../../app/docs/AUTH.md) for the full guide.

## 2. Performance — 60s → 20s on RAG queries

**Before**: a RAG query (the most common type) took 60+ seconds and
sometimes produced no answer.

**Why it happened** (measured, not guessed):
1. **Double Ollama call**: `run_agent_streaming` called `ollama_chat` once
   to check for tool calls, then **again** with `ollama_chat_streaming` to
   stream the final response. Each call was ~2.7s warm, ~7s cold → +5-10s
   per response.
2. **Agent loop never terminated**: the model would call `search_docs`,
   read the result, and call `search_docs` *again* with a different query.
   With `MAX_ITER=5`, this filled all 5 iterations with no final answer.
3. **`thinking` event never reached the client**: `stream_agent` did
   `list(run_agent_streaming(...))`, which consumed the entire generator
   before the SSE started. The "Pensando..." indicator never appeared
   until the response was already done.

**What I fixed**:
- **Reuse first response** in `run_agent_streaming`: the content from
  `ollama_chat` is emitted in chunks of 4 chars, no second Ollama call.
  Saves ~2-3s per response.
- **Early-stop on oscillation**: if 2 consecutive iterations call the same
  set of tools, the loop terminates. This is the main fix for the 60s
  RAG case.
- **`MAX_ITER=3`** (down from 5): typical RAG queries finish in 1-2 iter.
- **Producer/queue SSE pattern**: replaced `list(generator)` with a
  thread that pushes events to an `asyncio.Queue`. The coroutine `await`s
  one event at a time, so the client sees "thinking" within 2 seconds.
- **System prompt rewrite**: explicit examples of "when to stop" and
  "no more than 2 tools chained". 3b models need very concrete examples.

**Before/after on RAG query** (RTX 3050, `qwen2.5:3b`):

| | Wall | Tool calls | Iter | Answer |
|---|---|---|---|---|
| Before | 69.4s | 5 | 5 | none (hit MAX_ITER) |
| After | 20.2s | 1 | 1 | 80 tokens |

That's a **3.4x speedup** on the worst case, and the answer actually
arrives now.

## 3. Auto-scroll that respects the user

**Before**: `scrollToBottom()` used `requestAnimationFrame` once after each
event. The DOM kept growing as tokens streamed in, so the scroll position
lagged behind by several seconds. Result: user sees the response "stuck"
near the top, or scrolled to a weird middle position.

**The fix** (`isAtBottom` + `startAutoScroll`):
- A `requestAnimationFrame` loop runs while the chat is active
- It calls `scrollToBottom()` **only if the user is within 60px of the
  bottom** (`isAtBottom()` check)
- If the user scrolled up to read something, we **don't jump them back**
- When the response ends, `stopAutoScroll()` forces one final scroll to
  the bottom

**Also fixed** (related): the `flex: 1` on `.chat-area` was the wrong
shortcut. The chain `display: grid` (app) > `display: flex` (main) >
`flex: 1` (chat-area) needed `min-height: 0` on the middle container to
make `overflow-y: auto` actually work. Without it, the chat-area grows
to fit its content and there's never any overflow.

```css
.main { display: flex; flex-direction: column;
        min-width: 0; min-height: 0; height: 100%; }  /* added */
.chat-area { flex: 1 1 0; min-height: 0; overflow-y: auto; }  /* changed */
```

This is a classic CSS Grid + Flexbox interaction that's easy to miss.
The symptom is "I can see content but the scroll bar is gone".

## 4. Test suite grew from 89 to 93

New tests in v0.3:
- `test_login_rejects_wrong_password` / `test_login_rejects_missing_user` /
  `test_login_accepts_correct_credentials`
- `test_me_requires_token` / `test_me_rejects_invalid_token` /
  `test_me_rejects_tampered_token` / `test_me_accepts_valid_token`
- `test_models_requires_auth` (was `test_models_endpoint`)

All updated to use a new `auth_client` fixture that:
1. Resets the rate limit storage (autouse, to avoid 429s between tests)
2. Logs in as `admin`/`admin123`
3. Adds the JWT to subsequent requests

Lesson learned: when you add an autouse fixture that affects global state
(rate limit storage, db connection, etc.), make sure to also clean up in
the fixture's teardown — otherwise the last test's state bleeds into the
next test session.

## 5. Stripped `[TAREA_COMPLETADA]` from output

The base `qwen2.5:3b` model emits a `[TAREA_COMPLETADA]` token at the end
of its responses (control token from the system prompt). The user sees it
in the chat as a weird suffix. Fix: strip it in two places:
- `agent/run.py:format_response()` — backend final cleanup
- `chat_static/index.html:md()` — frontend, in case the token leaks
  through the stream before the backend's `format_response` runs

Defense in depth: if either layer is bypassed, the other catches it.
